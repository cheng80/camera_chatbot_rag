# 용어 사전

이 문서는 RAG를 처음 접하는 개발자를 기준으로 프로젝트 용어를 정리한다.
앞으로 문서와 대화에서는 가능한 한 `한글(English)` 형식으로 함께 표기한다.

## 기본 개념

| 용어 | 쉬운 설명 | 이 프로젝트에서 하는 일 |
|---|---|---|
| 검색 증강 생성(RAG, Retrieval-Augmented Generation) | AI가 그냥 기억으로 답하지 않고, 먼저 문서를 찾아본 뒤 그 근거로 답하는 방식 | Panasonic LUMIX PDF 매뉴얼에서 관련 페이지를 찾고, 그 페이지 근거로 기능 카드를 만든다. |
| 하이브리드 검색(Hybrid Search) | 의미 검색과 키워드 검색을 같이 쓰는 검색 방식 | “흔들림 줄이기” 같은 자연어와 “Boost I.S.” 같은 정확한 기능명을 둘 다 찾는다. |
| 의미 검색(Vector Search) | 문장의 뜻이 비슷한 문서를 찾는 검색 | 사용자가 기능명을 몰라도 비슷한 의미의 매뉴얼 내용을 찾는다. |
| 키워드 검색(Keyword Search, FTS/BM25) | 단어가 정확히 들어간 문서를 찾는 검색 | “제브라 패턴”, “LUMIX Lab”처럼 정확한 명칭을 빠르게 찾는다. |
| Elasticsearch | 대량 문서 검색, 형태소 분석, BM25, 필터 검색을 제공하는 검색 엔진 | 초기에는 FTS5로 기준선을 만들고, 평가셋에서 한계가 확인되면 검색 어댑터로 추가한다. |
| 별칭 검색(Alias Search) | 사용자가 쓰는 쉬운 표현을 공식 기능명과 연결하는 검색 | “나중에 초점 고르기”를 “포스트 포커스(Post Focus)”와 연결한다. |
| 규칙 기반 처리(Rule-based Processing) | 사람이 정한 규칙으로 입력을 해석하는 방식 | 모델명, 모델 별칭, 조사, 하이픈 차이를 먼저 안정적으로 처리한다. |
| 재정렬기(Reranker) | 검색 후보를 다시 점수화해 더 맞는 결과를 위로 올리는 단계 | 초기에는 생략 가능하고, 검색 품질이 부족할 때 추가한다. |
| 질의 정규화(Query Normalization) | 사용자가 입력한 검색어를 검색기가 잘 이해하는 형태로 다듬는 작업 | `G9M2 제브라 패턴`에서 모델명을 필터로 분리하거나, 띄어쓰기/하이픈 차이를 줄인다. |
| 질의 제어 문구(Query Control Phrase) | 검색 의도는 알려주지만 문서 검색에는 불필요한 표현 | `어디서 설정해?`, `어떻게 설정해?`를 제거해 핵심 기능명만 검색한다. |

## 문서 처리

| 용어 | 쉬운 설명 | 이 프로젝트에서 하는 일 |
|---|---|---|
| 문서 등록부(Document Registry) | 어떤 PDF가 프로젝트에 들어왔는지 적어두는 목록 | `document_id`, 파일명, 모델명, 언어, 문서 종류를 관리한다. |
| 모델 등록부(Model Registry) | 어떤 카메라 모델을 지원하는지 적어두는 목록 | `DC-G9M2`, `DC-S1M2`, `DC-TZ99` 같은 모델 ID를 관리한다. |
| PDF 로더(PDF Loader) | PDF를 검색에 쓰기 좋은 텍스트/구조 데이터로 바꾸는 도구 | pypdf, PyMuPDF, OpenDataLoader PDF로 페이지 텍스트, 표, 좌표를 뽑는다. |
| pypdf | Python만으로 PDF 글자를 뽑는 가벼운 라이브러리 | OpenDataLoader PDF의 CLI가 실패하거나 설치되어 있지 않을 때 쓰는 대체 로더(Fallback Loader)다. 구형 PDF처럼 구조화 로더 CLI가 실패하는 문서에서 텍스트를 회수한다. |
| OpenDataLoader PDF | PDF를 JSON/Markdown/Text로 바꾸는 구조화 로더 | 좌표(Bounding Box)와 구조화 요소(Structured Element)를 보존해 출처 하이라이트에 활용한다. |
| 기본 로더(Primary Loader) | 먼저 시도하는 PDF 추출 도구 | 현재는 OpenDataLoader PDF를 먼저 써서 구조와 좌표를 얻는다. |
| 대체 로더(Fallback Loader) | 기본 로더의 허용된 실패를 처리하는 예비 도구 | 구형 PDF에서 OpenDataLoader CLI가 실패하면 pypdf로 페이지 텍스트를 추출한다. 빈 결과나 페이지 수 불일치는 무결성 실패로 보고 중단한다. |
| 페이지 텍스트 추출(Page Text Extraction) | PDF 각 페이지에서 글자를 뽑는 작업 | 검색 색인과 근거 검증에 쓸 원문 텍스트를 만든다. |
| 페이지 이미지 렌더링(Page Image Rendering) | PDF 페이지를 이미지로 저장하는 작업 | 사용자가 출처 페이지를 눈으로 확인할 수 있게 한다. |
| 조각(Chunk) | 긴 문서를 검색하기 좋게 나눈 작은 단위 | 페이지/섹션 단위로 매뉴얼을 쪼개 검색 후보로 사용한다. |
| 출처 참조(Source Reference, Source Ref) | 답변의 근거가 되는 문서/페이지 정보 | 기능 카드에 `document_id`, `model_id`, `page`를 붙인다. |
| 좌표(Bounding Box) | PDF 페이지 안에서 문단이나 표가 있는 위치 정보 | 출처 문단을 PDF 뷰어에서 하이라이트할 때 쓴다. |
| 읽기 순서(Reading Order) | PDF 안의 글을 사람이 읽는 순서대로 정렬한 결과 | 다단 문서나 표가 섞인 페이지를 올바르게 검색하기 위해 필요하다. |

## 답변 검증

| 용어 | 쉬운 설명 | 이 프로젝트에서 하는 일 |
|---|---|---|
| 근거 검증(Evidence Evaluation) | 검색 결과가 질문에 답할 만큼 충분한지 확인하는 단계 | 찾은 매뉴얼 페이지가 실제로 해당 기능을 설명하는지 검사한다. |
| 출처 보호(Source Guard) | 근거 없는 답변이 나가지 못하게 막는 규칙 | PDF 페이지 근거가 없으면 기능 카드를 만들지 않거나 `insufficient_evidence`로 응답한다. |
| 모델 분리(Model Isolation) | 한 모델의 기능을 다른 모델 기능처럼 말하지 않게 막는 규칙 | S1M2 기능을 G85 기능처럼 보여주는 오류를 막는다. |
| 모델 혼합 오류(Model Mix Error) | 서로 다른 모델의 정보가 섞이는 문제 | 사용자가 선택한 모델과 다른 모델의 기능이 답변에 들어가는 경우다. |
| 근거 부족(Insufficient Evidence) | 업로드된 PDF에서 확실한 근거를 찾지 못한 상태 | AI가 추측하지 않고 “확인된 근거 없음”으로 처리한다. |

## 기능 카드와 지식층

| 용어 | 쉬운 설명 | 이 프로젝트에서 하는 일 |
|---|---|---|
| 기능 카드(Feature Card) | 검색 결과를 사용자가 보기 쉬운 카드로 정리한 답변 | 기능명, 요약, 지원 모델, 사용법, 주의사항, PDF 출처를 보여준다. |
| 기능 위키(Feature Wiki) | 기능별로 정리한 내부 Markdown 지식 문서 | 검색 보조와 기능명 표준화에 쓴다. 최종 근거는 항상 PDF다. |
| 검증됨(Verified) | 위키 내용이 PDF 근거와 맞는지 확인된 상태 | `verified=false` 위키는 답변 근거가 아니라 검색 힌트로만 쓴다. |
| 그래프 라이트(Graph-lite) | 모델, 기능, 메뉴, 앱, 문제해결 관계를 가볍게 연결한 구조 | “이 기능을 지원하는 모델은?” 같은 비교 질문으로 확장하기 위한 기반이다. |
| 관계(Relation, Edge) | 두 항목 사이의 연결 | 예: `DC-G9M2 supports Boost I.S.`, `Feature described_in Page 269`. |

## API와 UI

| 용어 | 쉬운 설명 | 이 프로젝트에서 하는 일 |
|---|---|---|
| 정적 웹 UI(Static Web UI) | HTML/CSS/JavaScript 파일을 서버가 그대로 제공하는 화면 | 초기 웹 화면을 빠르게 만들고 FastAPI API와 연결한다. |
| 백엔드 API(Backend API) | 화면이 요청을 보내고 데이터를 받는 서버 기능 | 검색, 문서 목록, 기능 카드, 피드백을 제공한다. |
| API 경계 검증(API Boundary Validation) | 서버가 처리하기 전에 요청값을 안전한 범위로 검사하는 단계 | 빈 질의, 너무 긴 질의, 비정상 모델 ID를 422 응답으로 거절한다. |
| PDF 뷰어(PDF Viewer) | 사용자가 PDF 출처 페이지를 확인하는 화면 | 기능 카드의 출처 버튼에서 해당 페이지로 이동한다. |
| 피드백 로그(Feedback Log) | 사용자가 답변이 맞는지 남긴 평가 기록 | 검색 품질 개선과 평가셋 보강에 사용한다. |

## 평가 지표

| 용어 | 쉬운 설명 | 이 프로젝트에서 하는 일 |
|---|---|---|
| 상위 5개 정답 포함률(Retrieval Top-5 Accuracy) | 검색 결과 5개 안에 정답이 있는 비율 | 목표는 85% 이상이다. |
| 상위 K개 결과(Top-K Results) | 검색기가 점수순으로 돌려주는 앞쪽 K개 결과 | 초기 평가에서는 Top-5 안에 기대 문서/페이지가 들어오는지 확인한다. |
| 검색 평가셋(Search Evaluation Set) | 검색 품질을 반복 측정하기 위한 대표 질문 목록 | `data/eval/search_eval_cases.json`에 질의, 모델, 기대 문서, 기대 페이지를 적는다. |
| Seed 평가셋(Seed Evaluation Set) | 평가 체계를 만들기 위한 초기 작은 평가셋 | 현재 50개로 구성되어 있으며 스키마와 리포트 검증에 쓴다. |
| 개발 평가셋(Dev Evaluation Set) | 검색 로직을 바꾸며 자주 확인하는 평가셋 | 100개 수준으로 확장해 튜닝 중 회귀를 잡는다. |
| 잠금 평가셋(Locked Evaluation Set) | 튜닝에 직접 쓰지 않고 최종 비교에 쓰는 평가셋 | 최소 300개로 만들어 FTS5, Elasticsearch, 벡터 검색을 비교한다. |
| 약라벨(Weak Label) | 사람이 직접 검수하지 않고 규칙이나 문서 구조로 만든 임시 정답 | 섹션 제목, 목차, 메뉴 목록, 페이지 청크를 조합해 기대 페이지 후보를 만든다. |
| 생성 근거(Source Method) | 평가 케이스가 어떤 방식으로 만들어졌는지 표시하는 값 | `manual_seed`, `section_title_weak_label`처럼 케이스 신뢰도를 구분한다. |
| 검색 로그(Search Log) | 사용자가 입력한 검색어와 검색 결과 상태 기록 | 웹 프로토타입 이후 실제 커뮤니티 질의를 평가셋으로 확장하는 데 쓴다. |
| 기준선(Baseline) | 개선 전 현재 성능을 기록한 값 | 검색 로직을 바꾼 뒤 실제로 좋아졌는지 비교하는 기준이다. |
| 문서 적중률(Document Hit Rate) | 검색 결과 안에 기대 문서가 포함된 비율 | 모델 필터와 문서 선택이 맞는지 확인한다. |
| 페이지 적중률(Page Hit Rate) | 검색 결과 안에 기대 페이지가 포함된 비율 | 출처 링크가 실제 관련 페이지로 이어질 가능성을 본다. |
| 출처 페이지 정확도(Source Page Accuracy) | 출처 링크가 실제 관련 페이지로 가는 비율 | 목표는 95% 이상이다. |
| 카드 스키마 통과율(Card Schema Valid Rate) | 기능 카드 JSON 형식이 맞는 비율 | 목표는 98% 이상이다. |
| PDF 링크 성공률(PDF Link Success Rate) | 출처 페이지 링크가 정상으로 열리는 비율 | 목표는 99% 이상이다. |
| 지연 시간 95퍼센타일(Latency P95) | 대부분 사용자가 기다리는 검색 시간 기준 | 검색 응답 3초 이하를 목표로 한다. |

## 앞으로의 표기 규칙

- 처음 등장하는 용어는 `한글(English)`로 쓴다.
- 약어는 처음에 풀어쓴다. 예: `검색 증강 생성(RAG, Retrieval-Augmented Generation)`.
- 구현 설명에서는 “무슨 기능을 위한 것인지”를 한 문장으로 붙인다.
- 확정된 프로젝트 용어는 이 문서에 추가한다.
